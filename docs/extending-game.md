# 扩展游戏：从开发任务找到修改位置

本页供人工贡献者与代码助手按任务查阅，不要求先读完整架构历史。先看下面的落点，再打开对应实现和测试。状态持有与同帧顺序见[架构地图](architecture-map.md)，命令和验证范围见[测试与验收](testing.md)。

## 先决定新增内容是什么

| 要做的事 | 主要修改位置 | 不必随之增加的结构 |
| --- | --- | --- |
| 调整已有角色数值 | `shared/game/characters/catalog.js` 或角色配置 | 新状态机、动作或端口 |
| 新角色使用已有技能能力 | `characters/<角色>/extension.js`、`assembly/registry.js` 与数值目录 | Ship/Team 专属字段、中央角色分支 |
| 新的普通定时增益 | 角色声明、现有 ShipStatus 操作与展示元数据 | 单独计时器、帧末事件队列 |
| 形态、叠层、来源归属、持续行为 | 角色目录内明确的状态所有者；需要实体交互时加适配 | 空的 runtime/port/projection 三件套 |
| 新 AI 技能判断 | `ai/policy/characters/`；缺事实时扩展观测桥 | 向策略提供 Ship/Team 或写入模拟的后门 |
| 新开局配置或胜负条件 | `runtime/battle-mode.js` | 新版 MatchSimulation、复制帧推进循环 |
| 新房间组织方式 | `server/room.js`、`room-lifecycle.js` 及对应客户端入口 | 第二套战斗规则 |
| 新显示效果 | `src/battle/render/` 与需要的只读快照字段 | 在插值或绘制中更新模拟 |

目录是职责边界，不是每个调用必须经过的流水线。端口只用于跨越状态所有者、隔离事实/命令或保持同步事务；同一角色内部的小函数直接调用即可。新增抽象应能说明它消除了哪一处重复或错误权限。

## 新增角色

1. 从相近角色的 `extension.js` 开始，只填写需要的字段。阿虚展示简单主动技能，长门展示队级状态和固定阶段，兔女郎展示多阶段状态与来源关系。不要直接复制最复杂角色的全部结构。
2. 在 `catalog.js` 配置身份、数值和技能元数据，在 `assembly/registry.js` 登记声明。注册次序仅用于构造；运行顺序由钩子/阶段内的明确顺序决定。
3. 已有主动技能使用 `activeSkills.flagship/sub` 和技能端口。资格、扣费、退款、冷却、显形的约定沿用 `systems/skill-cycle.js`、`adapters/team-skill-port.js`；不要在角色中再实现一轮通用资格判断。
4. 独立状态由角色拥有，只通过操作推进。需要净化、移动、命中或固定阶段消费时声明钩子；只有真正在用的生命周期才接入。需要跨实体生成、转移或承伤时，使用领域操作并保持即时消费。
5. 增加 `projectShip/projectTeam` 或 `statusEffects` 只读输出；协议投影不会因为注册一个状态机而自动出现。补齐选角、技能文案、三语、素材和必要渲染；AI 档案单独说明如何使用技能。

`compileHooks` 的广播、独占、查询和顺序计算语义见[角色导航](../shared/game/characters/README.md#效果的接入与消费)。独占处理的 `false` 表示处理完成但失败；`null/undefined` 才表示交给后续处理者。净化和命中通知不能用独占语义。

`Ship`、`Team`、`BattleRuntime` 不为每个新角色添加一次 if/switch。确实缺少一种通用操作时，先给其真实所有者添加操作，再把窄能力提供给角色；不要同时保留字段赋值和新方法两条写路径。

## 新增效果：时间、规则与展示分别接入

普通定时效果可以复用 `ShipStatus` 的截止时刻和生效帧。例如下面声明一种可净化的定时增益，同时提供属性倍率与状态卡：

```js
export default {
  id: "new_character",
  positiveTimedEffects: ["newSignalUntil"],
  timedAttributes: [[30, { until: "newSignalUntil", multipliers: { damage: 1.25 } }]],
  activeSkills: {
    sub(port, meta) {
      port.activateEffect("newSignalUntil", meta.duration);
      return true;
    },
  },
  statusEffects: [[170, (ship, { timed }) => {
    timed("new_signal", ship.effects.newSignalUntil, 8);
  }]],
};
```

角色数值、状态元数据和翻译必须与示例同时补齐；实际代码中的持续时间读取角色数值定义，不重复维护 `8`。顺序 `170` 只是当前已有状态组之后的示意位置，接入时检查现有声明并选择语义正确的位置。编译器会拒绝重复顺序，不能靠注册先后来“碰巧正确”。

- **生命周期**：激活、延长、同帧保护与净化交给所有者。读取状态栏不得顺便清理到期效果。
- **规则作用**：普通定时倍率使用 `timedAttributes` 的截止字段与数值表，编译时拒绝未知属性、非法倍率和重复顺序。定时倍率阶段按显式顺序计算，再进入形态、队级强化等既有阶段；上例 `30` 必须与已有声明核对。仅新增普通倍率不改中央求值器。需要新的计算类型或事实时，再扩展 `attribute-facts.js` / `attribute-evaluation.js`；求值器仍只消费普通数据，不调用角色函数或读取世界。
- **展示**：在 `projection/status-effect-definitions.js` 声明图标、文案与类别，通过角色 `statusEffects` 提供资格、截止时刻和参数。公共投影器无需增加角色分支；复杂投影放到角色已有的 `projection.js`。
- **AI**：需要策略感知时，经 `ai/bridge/observation.js` 提供允许获知的事实；不能从显示快照、隐藏敌情或实体指针绕过观测边界。

叠层、持续结算游标、来源转移、伴随舰和复合形态不只是“一个 until 字段”，仍需专属状态所有者。共享读模型必须与权威状态分开；成员只读视图中的活实体也不能误当成不可变快照。

## 新增模式：先区分三个维度

| 维度 | 当前例子 | 负责的位置 |
| --- | --- | --- |
| 谁提交动作 | 玩家、单席 AI、双 AI | 模式默认席位、动作传输与 AI 桥 |
| 对局如何开始与结束 | 普通战斗、教程训练配置、歼灭胜负条件 | `runtime/battle-mode.js` |
| 房间与页面如何组织 | 单人页面、普通房、比赛房、观战 | 单人 session、服务端 Room、客户端页面 |

比赛房仍使用 pvp 战斗；观战不是另一套规则。不要让模式名称同时承担这三个维度。

新开局配置或胜负规则在 `battle-mode.js` 的 `modes` 登记普通规则对象，通过开局选项 `battleMode` 选择；它与控制席位用的 `mode` 分开。未知规则编号立即拒绝，旧 `tutorialMode` 仍作为默认选择。规则对象提供 `initialize` 与 `evaluateOutcome`。初始化只取得训练/开关等所需命令；求值只接收 `{ elapsed, aAlive, bAlive }` 事实，返回 `null` 表示继续，返回 `{ winnerSeat }` 表示候选结果（`winnerSeat: null` 是平局）。非歼灭终局附带非空字符串 `reason`，由运行时原子提交并投影为 `endReason`，房间与结算界面统一消费，不能让页面猜测结束原因。BattleRuntime 在原阶段提交终局，MatchSimulation 决定下一步是否继续推进时间。

如果新玩法需要比分或占领进度，显式扩展事实样本及对应所有者；不要把完整 Match 传给纯求值器。只有新增持续模式状态时才引入其状态组件。多队伍、不同地图拓扑或新协议动作需要单独评估相关契约，不能假装填一张模式表就能支持。

## 开发完成前检查实际链路

| 改动 | 必须能解释的调用与数据流 | 验证入口 |
| --- | --- | --- |
| 新角色/效果 | 输入 → 资格/扣费 → 效果所有者 → 同帧后续查询 → 快照 | 核心角色测试、架构专项；改规则加权威一致性 |
| 净化/死亡/转队 | 谁清理、何时清理、同帧保护、失败是否留下半提交 | 相关所有权和事务专项 |
| 状态显示 | 存活/过期/净化 → 只读投影 → 对战/观战展示 | `test:ui:status`，角色特殊表现另补专项 |
| AI | 合法观测 → 判断 → 动作端口 → 重新观测 | 核心 AI、观测/动作测试及 AI 模拟 |
| 模式 | 初始化顺序 → 每帧事实 → 胜负候选 → 一次提交 → 停步 | `verify-battle-mode`、教程/终局、权威与服务端测试 |

架构重构使用现有固定回放，不能重录基线使测试变绿。真正改变游戏规则时按[版本约定](architecture.md#协议版本约定)处理。测试需要跳时只使用独立 `ScenarioSimulation`，生产入口、权威对照和完整回放仍使用真实 MatchSimulation。

本框架不要求为每种功能增加更多层级。它让修改位置、状态所有者和执行时机可定位；是否容易开发，应继续用具体新增功能和回归结果检验，不能仅凭图无环或测试为绿下结论。
