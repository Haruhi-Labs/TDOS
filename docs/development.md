# 开发与协作

## 环境与事实来源

使用锁文件中的依赖：首次安装运行 `npm ci`。当前 Vite 8 要求 Node.js `^20.19.0 || >=22.12.0`，建议使用满足该范围的 LTS 版本；升级依赖时同时核对运行时要求。

`npm run dev` 启动前端；联机开发另开终端运行 `npm run start:server`。Vite 将 `/ws` 代理到本地 21246，将 `/api` 与 `/uploads` 代理到本地 17777。真实身份联调还需主站 news 前端（5204）及测试 Rust 后端（17777）。普通游戏开发无需启动真实身份链路。

| 问题 | 事实来源 |
| --- | --- |
| 命令、依赖版本 | [package.json](../package.json)、[锁文件](../package-lock.json) |
| 开发代理、构建基路径 | [vite.config.js](../vite.config.js) |
| 规则、动作与兼容版本 | [架构](architecture.md)指向的 `shared/` 模块 |
| 验收覆盖与测试环境 | [测试与验收](testing.md)、对应 `scripts/` 文件 |
| 进程、发布和数据边界 | [运维](operations.md)；执行前核对目标环境现状 |

文档与实现不一致时，先确认这是实现缺陷还是说明过期，再修正相应一侧；不要把现有代码自动当作正确需求。运行日志、旧提交和历史评测只能证明当时状态。

## 定义要交付的结果

简单问题直接描述预期行为即可。跨模块或难以验收的任务，可补齐下面这些信息；缺失但可从代码和上下文推断的内容由执行者补足，不把模板变成开工门槛。

```text
目标：谁在什么场景下，应得到什么可观察结果。
边界：涉及哪些模式/页面/协议，哪些兼容性或数据必须保留。
验收：用什么输入、界面或日志证明成功，以及需要覆盖的失败路径。
完成：实现并运行相关验证，修复本次引入的问题，说明剩余限制。
```

例如：“修复观战航线颜色。A/B 席位在切换所选舰船后仍保持固定阵营色，航线只显示当前选舰；覆盖单人、联机和观战，并给出实际画面证据。”这里规定结果与边界，具体工具、函数拆分和执行顺序由实现需要决定。

## 实现与交付

普通开发分支从 `dev` 开始并创建目标为 `dev` 的 PR；发版、热更新与部分提交晋级统一见[发布流程](operations.md)。当前开发不直接推送 main，也不以 main 合并自动触发生产部署。

- 先查看已有改动和受影响入口；沿用现有模块职责、ES modules 风格和命名。新增抽象应解决当前的重复或边界问题。
- 修复行为缺陷时优先建立能复现问题的行为测试。纯文案、可逆样式微调不为了凑数量新增测试。
- 共享规则、渲染、身份和统计的边界见架构；测试选择见测试文档，不在多个文档重复维护命令清单。
- 功能改变时更新对应开发说明。玩家可见的版本变化才进入 `src/changelog/`，内部规范调整不发布游戏更新日志。
- 提交前检查差异和 `git diff --check`，只暂存本工作项文件；一个提交保持一个可解释、可验证的目的，不混入已有无关改动。
- 交付以实际结果收尾：变化是什么，哪些检查通过/失败/未运行，限制在哪里。通过相关检查后无需无依据地重复全量测试；出现新改动或新风险时再补验证。

## 文档与约束如何维护

此次整理参考 OpenAI 的 [Rethinking skills and prompts for GPT-6 Astra](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)。采用按需提供上下文、明确结果和行动边界的思路。下面的文件分工与测试选择是本项目结合代码作出的设计，不是文章规定的通用流程。

| 放在哪里 | 放什么 | 何时加载 |
| --- | --- | --- |
| [AGENTS.md](../AGENTS.md) | 跨任务有效的项目底线与文档入口 | 仓库内工作 |
| [README](../README.md) | 玩家与新开发者需要的简介、启动入口 | 了解或启动项目 |
| 本文 | 开发环境、交付方式与规范维护 | 开发协作发生疑问时 |
| 架构、测试、运维文档 | 各自领域的边界与可操作说明 | 对应任务发生时 |
| 代码与测试 | 机器可检查的契约、失败回归 | 实现和验证时 |
| 任务描述或提交说明 | 本次目标、取舍和验收证据 | 当前工作项 |

新增长期规则前，确认它保护的具体行为或资产、适用条件及验证方法。优先修复测试、脚本或领域文档；仅当规则跨任务成立时才放进 `AGENTS.md`。过期路径直接纠正，同一事实只保留一个详细说明，其他地方链接过去。

当前仓库无需另建技能来包装通用开发流程。出现反复使用且确有项目专用知识的工作流时，再考虑技能：描述只写清准确触发条件，入口只做简短路由，细节放按需参考。避免因“游戏”“测试”等宽泛关键词自动加载一整套流程。

这些约定供不同模型和人工贡献者使用，不依赖特定模型名称、固定推理步骤或固定工具调用次数。

## 验证规范本身是否有用

调整说明或测试编排后，用有代表性的任务检查适用性：

| 场景 | 预期行为 |
| --- | --- |
| 修正文档错字 | 只检查差异、链接和命令准确性，不启动游戏全量测试 |
| 修改技能伤害或 AI 决策 | 定位共享规则、考虑规则版本，执行对应规则和权威一致性验证 |
| 调整观战视觉 | 检查共享表现及相关画面，不把构建成功当作视觉验收 |
| 修改身份/统计 | 保留游客能力，验证验签或公开字段隔离，不接触生产身份库 |
| 仅发布测试站静态前端 | 完成本地候选门禁，按授权只切换测试前端，不连带重启联机服务 |

记录实际漏检、误触发、无效阅读或重复确认，再决定删改哪条说明。上表是规范评审案例，不是已执行的模型评测；没有真实对照运行时不宣称效率或质量提升了多少。
