# 通用强化学习训练环境

本目录只保存可审查的小型源码、配置和依赖锁。虚拟环境、缓存、轨迹、检查点与模型均存放在 `/Volumes/data/haruhi-rl`，不得写入仓库或系统盘。

## 学习契约

- 一个通用策略控制任意角色组合，不为具体角色维护手写策略或独立模型。
- Actor 只能读取玩家可获得的原始信息，不读取完整敌方状态、现有 AI 的 belief 图或派生战术标签。
- 初始策略随机初始化，不使用现有规则 AI 的行为克隆数据。
- 初始奖励只包含胜、负、超时结果；增加任何辅助奖励前必须做独立消融并记录理由。
- 角色身份与技能槽可以作为不透明标识输入；技能用途、角色打法和战区价值由策略通过交互学习。
- 无效动作通过规则生成的合法性掩码排除；点目标/战区目标标记仅描述动作语法，不提供动作收益信息。

## 共享接口

- `shared/training/observation.js` 从指定玩家席位构建版本化原始观察。己方舰队状态完整可见；敌方实体必须进入该席位的 `visibleEnemyIds` 才会出现；长门雷达只输出带误差的私有回波，移除真实实体编号与真实距离比例，并把误差参数量化到画面可辨别粒度。
- `shared/training/actions.js` 定义角色无关的组合动作、合法性掩码和权威协议解码。策略可分别控制每艘已分离舰的航线、档位、急刹和副舰技能，同时控制分舰、侦察机与旗舰技能。
- `shared/training/environment.js` 提供无规则 AI 的双席位单局环境和可交错推进的批环境。默认每 3 个 30Hz 权威 tick 决策一次（10Hz），超时 180 秒；这些参数均可由实验配置覆盖。
- 弹丸、光束与朝仓视野波按现有客户端绘制规则作为公开效果；敌方航线、冷却、隐藏角色身份和未进入视野的实体不进入 Actor 观察。
- 观察使用可变长实体列表，并以每艘舰的 `controlKey` 对齐共享动作头，为以后扩展 3v3 保留接口；固定尺寸张量化由训练进程负责，不把 1v1 的三舰数量写进网络结构。

运行 `npm run test:training:contract` 可执行隐藏真值变形测试、雷达席位隔离测试、公开效果测试和通用动作权威入口测试；`npm run test:training:environment` 验证批环境确定性、全角色均匀抽样、双方权威动作和纯终局奖励。

## 数据盘目录

运行 `scripts/setup-rl-runtime.zsh` 后使用以下目录：

```text
/Volumes/data/haruhi-rl/
├── python/       uv 管理的 Python 运行时
├── venv/         锁定依赖的虚拟环境
├── cache/        uv、pip、Torch 与通用缓存
├── tmp/          临时与编译文件
├── datasets/     可再生成的轨迹数据
├── runs/         训练指标和实验元数据
├── checkpoints/ 训练检查点
├── league/       自我博弈历史对手池
└── models/       经过评估的导出模型
```

大型目录必须保持在 Git 管理范围之外。训练记录只把配置、代码提交号、随机种子、摘要指标和产物哈希写回项目。

后续命令统一通过 `scripts/run-rl.zsh` 执行，例如：

```bash
scripts/run-rl.zsh python -m pytest
```

该入口固定复用数据盘 Python、虚拟环境、缓存与临时目录，并使用 `--locked --no-sync`，不会在仓库或系统盘临时创建另一套环境。Python 侧通过 `haruhi_rl.bridge.NodeBatchBridge` 启动本地 Node 批环境；通信只承载共享观察、动作、奖励和终局信息。

`haruhi_rl.tensors` 将双方席位帧编码为分类型的实体集合张量和合法动作 mask。角色、技能形态、单位类型与轨迹编号都只做稳定哈希，不写入语义；数值仅按固定物理量级缩放。默认容量同时为未来 3v3 预留，任何类别溢出都会中止并报告，不会按距离、血量或威胁度静默筛选实体。

`haruhi_rl.model.HaruhiUniversalPolicy` 对每类实体使用共享编码器和带 mask 的注意力汇聚，保留己方舰船 token 供共享逐舰动作头使用，再以 GRU 保存部分可观测战局的历史。所有角色共用同一网络；输出覆盖航线终点与曲率、档位、急刹、分舰、侦察机、旗舰技和副舰技。价值头读取与 Actor 相同的公平观察，初版不使用隐藏真值中央 Critic。

`haruhi_rl.rollout` 让同一策略从随机初始化同时控制双方，并按席位分别编码观察；正式更新采用完整局采集：冻结策略直到每个并行环境结束第一局，屏蔽较早结束环境随后产生的填充局，再统一更新。这保证纯终局奖励能够覆盖整局动作，不跨策略版本拼接残缺轨迹。`haruhi_rl.ppo` 以短序列重放 GRU 状态后执行 clipped PPO；默认 `gamma=1`、`GAE lambda=1`，不通过折扣暗中加入“越快结束越好”的目标。对局种子由 `haruhi_rl.seeds` 在 Python 侧逐流调度并可随检查点保存。

## 系统盘保护

依赖和训练产物位于数据盘并不能阻止 macOS 在统一内存紧张时把交换文件写入系统盘。训练监督器必须同时监控系统盘可用空间、进程常驻内存和系统交换量；系统盘低于安全线或交换量持续上升时，应先保存检查点再暂停采样，不得依靠系统自动耗尽空间。

`haruhi_rl.resources` 的默认启动门槛为：系统盘至少 4 GiB、数据盘至少 40 GiB、交换空间至少 2 GiB，单个训练进程 RSS 不超过 10 GiB。门槛只控制训练进程，不修改、暂停或重启游戏服务。

正式训练入口为 `scripts/train-rl.zsh --config training/configs/universal-v0.yaml`。入口先在未加载 PyTorch 的轻量进程中执行预检；训练循环在每轮开始、完整局采集过程中和参数更新后检查资源，并在触线时释放轨迹内存、原子保存 `paused_resource_guard` 检查点后退出。检查点、SHA-256 清单、JSONL 指标和 TensorBoard 日志全部写入 `/Volumes/data/haruhi-rl`。默认配置从 2 个并行环境起步，以完整局采集降低系统内存与 swap 风险，确认稳定后才逐步提高并发。

历史检查点通过 `haruhi_rl.league.LeagueRegistry` 形成联赛池，使用确定性 PFSP 权重偏向当前策略较难战胜的对手，同时保留全池覆盖。首轮由当前策略共享控制双方，形成第一个历史快照；之后 `LeagueSelfPlayCollector` 每局随机安排当前策略的红蓝席位，另一侧加载不可变历史模型，默认每 5 轮加入一个新快照。两边都只读取各自公平观察，PPO 只更新当前策略席位。规则 AI 不进入联赛训练，只在独立评估阶段作为基准。

`haruhi_rl.evaluation` 在独立环境中让候选策略对战当前 `master` 规则 AI，默认使用镜像阵容、红蓝换边和覆盖全部旗舰角色的用例。候选仍只获得公平 Actor 观察；评测结果按席位和旗舰角色拆分，后续晋级门槛不会只看一个总胜率。

正式命令为 `scripts/evaluate-rl.zsh --checkpoint <数据盘检查点>`，并使用检查点内封存的模型与张量配置同时运行镜像及交叉阵容。至少 128 局、计入超时惩罚后的得分率不低于 50%、95% 下界不低于 45%、超时不超过 5%、红蓝差不超过 10 个百分点且各旗舰得分率不低于 35% 时才进入候选；只有 95% 下界达到 50% 才标记为“已证明不弱于 master”。

通过评测的检查点可用 `scripts/export-rl.zsh --checkpoint <数据盘检查点>` 导出 ONNX 策略核心。导出保留动态 batch、固定实体容量和外部 GRU 隐状态，随后由 ONNX Runtime 对全部输出逐项复算；模型、SHA-256、输入输出契约和最大数值误差写入数据盘 `models/`。当前阶段不自动把未达标模型接入正式客户端。

浏览器候选运行时使用 `shared/training/tensors.js` 直接编码同一份公平观察；它输出 ONNX 可接收的 `Float32Array`、`BigInt64Array` 和布尔掩码。`npm run test:training:tensors` 与 Python 测试会对包含全部实体类型和状态的合成帧逐元素比较两端结果，防止训练与客户端输入静默漂移。

`shared/training/policy-action.js` 将 ONNX 输出确定性解码为现有权威动作协议，非法输出会继续受同一份动作掩码约束。浏览器与 Python 会使用同一组真实网络输出逐字段比较最终动作，保证候选评测和客户端执行语义一致。

`shared/training/browser-policy.js` 管理浏览器推理会话、GRU 隐状态和回合重置，并在加载时强制校验观察/动作/张量版本、输入输出顺序及模型 SHA-256。它不被当前游戏入口引用，也不包含 ONNX Runtime 依赖；只有达标候选经明确接入后才会增加客户端下载与推理开销。
